ATLAS — Phase 3: Intelligence Correlation and Investigation

Context

Extend the existing ATLAS application from Phases 1 and 2.

The application already supports target management, scope validation, intelligence collection and persistent observations.

This phase implements the core product functionality: building an interconnected intelligence profile.

Main objective

Transform independent reconnaissance observations into a searchable, evidence-backed knowledge graph that supports manual security investigations.

Functional requirements

Entity resolution

Implement deterministic entity normalization and deduplication.

Support normalization of:

Domain names.

IP addresses.

URLs.

Technology identifiers.

Certificate fingerprints.

Service identifiers.

Preserve original observed values alongside normalized values.

Do not merge entities based solely on uncertain similarities.

Correlation engine

Implement evidence-backed relationship types:

HAS_SUBDOMAIN

RESOLVES_TO

HAS_DNS_RECORD

USES_TECHNOLOGY

PRESENTS_CERTIFICATE

HAS_ENDPOINT

HOSTS_SERVICE

REDIRECTS_TO

OBSERVED_IN

Each relationship must contain:

Source entity.

Destination entity.

Relationship type.

Supporting observations.

First observed timestamp.

Last observed timestamp.

Confidence.

Current status.

Distinguish direct observations from inferred relationships.

A shared IP address must not automatically imply common ownership, especially when CDN or shared hosting infrastructure is involved.

Correlation must be deterministic and idempotent.

Investigation management

Users must be able to assign investigation statuses to assets:

Unreviewed

Reviewing

Reviewed

Needs follow-up

Archived

Allow users to:

Add investigation notes.

Create manual observations.

Attach evidence.

Add custom tags.

Bookmark assets.

Create manual relationships.

Record hypotheses separately from confirmed findings.

Historical intelligence

Implement observation history and target snapshots.

Preserve previous observations when an entity changes.

Support comparisons between two collection runs.

Detect:

Newly observed entities.

Newly observed relationships.

Modified metadata.

Changed DNS records.

Changed technology observations.

Assets no longer observed.

Do not classify an asset as removed based on a single failed or incomplete collection run.

Search

Implement searchable intelligence using SQLite indexes and FTS5 where appropriate.

Support filtering by:

Entity type.

Scope status.

Investigation status.

Technology.

Tags.

Observation date.

Confidence.

Input

The correlation engine consumes persisted observations generated by collectors or entered manually.

Example:

{
  "observations": [
    {
      "type": "dns_resolution",
      "subject": "api.example.com",
      "value": "192.0.2.10"
    },
    {
      "type": "dns_resolution",
      "subject": "dev.example.com",
      "value": "192.0.2.10"
    }
  ]
}

Output

An evidence-backed graph containing normalized nodes and typed relationships.

Example:

{
  "nodes": [
    {"id": "1", "type": "subdomain", "value": "api.example.com"},
    {"id": "2", "type": "subdomain", "value": "dev.example.com"},
    {"id": "3", "type": "ip_address", "value": "192.0.2.10"}
  ],
  "edges": [
    {"source": "1", "target": "3", "type": "RESOLVES_TO"},
    {"source": "2", "target": "3", "type": "RESOLVES_TO"}
  ]
}

Expose API endpoints for:

Entity search.

Entity relationships.

Graph neighborhood retrieval.

Investigation notes.

Investigation statuses.

Snapshot creation.

Snapshot comparison.

Observation history.

Graph queries must support pagination and bounded traversal.

Frontend requirements

Implement:

Intelligence search page.

Entity investigation workspace.

Related assets panel.

Evidence and observation timeline.

Investigation notes editor.

Snapshot comparison page.

Investigation status filters.

Users must be able to navigate between related entities without leaving the target workspace.

Testing requirements

Test:

Entity normalization.

Idempotent correlation.

Relationship provenance.

Historical observation preservation.

Snapshot comparison.

Incomplete collection handling.

Target data isolation.

Manual and automated observation separation.

Acceptance criteria

Repeated collection does not create duplicate graph nodes.

Every automatically generated relationship is traceable to evidence.

Users can investigate assets and persist their progress.

Historical changes are visible and comparable.

Graph traversal remains bounded.

Uncertain information is clearly distinguished from confirmed observations.

All existing and new tests pass.

Do not introduce an external graph database unless a demonstrated technical requirement makes SQLite insufficient.

Implement the complete phase and document the correlation rules.
